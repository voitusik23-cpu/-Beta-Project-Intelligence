# PROJECT_RULES — Beta Project Intelligence

Версия: 1.0 | Статус: обязательные правила проекта

## Роль
Beta Project Intelligence — самостоятельная Web3 Intelligence Platform для обнаружения, проверки и ранжирования ранних Web3-возможностей: stealth/formation, incubation, waitlist, private/public beta, testnet/devnet, points, grants, funded projects и late-entry opportunities.

Этот репозиторий — центр управления и документации. Он не заменяет существующую рабочую копию приложения.

## Сохранение существующего
- Не переписывать приложение с нуля и не менять архитектуру без доказанной необходимости.
- Не удалять и не перезаписывать базу, результаты сканирования, конфигурации и пользовательские данные.
- Не менять scoring, веса, фильтры и критерии отбора без отдельного согласования.
- Не затрагивать Forge-AI, KeyCore-Hub, AI-Agents и другие репозитории.
- Перед изменениями изучить структуру, git status, ветку, локальные изменения и сделать резервную копию.
- Не выполнять destructive migrations, массовое удаление, reset/clean, force push или переписывание истории.
- Не добавлять в Git секреты, API keys, cookies, tokens, private keys, seed phrases и персональные данные.

## Работа Codex
Перед каждым этапом:
1. Прочитать README.md, PROJECT_RULES.md, MASTER_TASK.md и соответствующее задание из tasks/.
2. Убедиться, что открыта правильная рабочая директория Beta Project Intelligence, а не Forge-AI/KeyCore-Hub.
3. Зафиксировать путь, ветку, git status, ключевые файлы и baseline тестов.
4. Сделать backup или использовать безопасную ветку/коммит.
5. Сначала исследовать причину, затем вносить минимально необходимые изменения.
6. Запустить релевантные тесты и проверить реальные UI-сценарии.
7. Сохранить отчёт в reports/ с точными путями и результатами.

Не останавливаться после плана, если задание требует выполнить работу. При реальном блокере описать его и не выдумывать результат.

## Доказательность
- Разделять подтверждённые факты, предположения и неизвестные данные.
- Не создавать фиктивные проекты, источники, показатели, рейтинги, funding rounds или метрики.
- Наличие URL не означает, что источник подключён.
- Для важных фактов хранить URL источника, дату проверки, тип источника и уровень доверия.
- Социальная публикация — сигнал, а не окончательное подтверждение.
- Неизвестные данные маркировать как неизвестные, а не подставлять фиктивные значения.
- Opportunity Score и Evidence Confidence — разные показатели.

## Безопасность Web3
- Не подключать кошельки, не подписывать сообщения и не отправлять транзакции автоматически.
- Не хранить seed phrases/private keys.
- Не обходить CAPTCHA, KYC, географические ограничения, anti-bot, Sybil detection, account limits и правила кампаний.
- Не автоматизировать массовую регистрацию аккаунтов.
- Действия с финансовыми последствиями требуют ручного решения пользователя.

## Продуктовые требования
- Основной язык интерфейса, описаний и выводов — русский.
- Имена проектов, тикеры, фонды и компании сохранять в оригинале.
- Официальные сайты и каналы должны быть кликабельными.
- Для проекта — досье с фактами, источниками, стадией, условиями участия, затратами, ограничениями и датой проверки.
- Не обещать airdrop, токены, прибыль или награды без официального подтверждения.
- Сохранять историю изменения рейтинга и причин.

## Контроль изменений
- Предпочитать отдельную feature-ветку и Pull Request.
- Не сливать изменения в main автоматически.
- Не коммитить .env, локальные базы, кэши и логи с секретами.
- Каждая миграция требует backup, rollback plan и теста на копии данных.
- В отчёте перечислять изменённые файлы, тесты, результаты, ограничения и способ ручной проверки.

## Definition of Done
Этап завершён только когда изменения реально внесены, тесты запущены, основные сценарии проверены, данные сохранены, отчёт приложен, а оставшиеся проблемы перечислены. Слова «готово» без доказательств не являются приёмкой.
