## Adapter and operational findings

- `app/discovery.py`: RSS (RSS 2.0 and Atom parsing) and GitHub repository search normalize candidates through `upsert_signal`; writes to `projects`, `project_sources`, `raw_items`, `project_reviews`, and `project_events`; duplicate `(source_id,url)` links are ignored. The UI reads source evidence through `/api/projects/{id}` and source health from `/api/sources`. DuckDuckGo uses a separate public HTML parser and does not use the shared retry helper.
- `app/monitoring.py`: scheduler checks enabled ACTIVE RSS/GitHub/DDG connectors at stored cadence (minimum 15 minutes); manual scan also allows ERROR/NEEDS VALIDATION connectors. Runs are serial. Exception details previously persisted raw strings; safe error summaries are now used.
- Rate control before fix: GitHub ran 16 search calls back-to-back; registered 120-minute cadence, but manual scans could trigger immediate requests. Current collector spaces query starts at least 7 seconds apart (about 8.6 requests/minute) and stops the current pass on 403/429. Shared fetch retry is limited to 429 and HTTP 500/502/503/504, maximum two retries, honoring numeric or HTTP-date `Retry-After` capped at 30 seconds. 403 is not retried. DDG keeps its 20-second timeout and does not retry.
- `GET /api/sources` now exposes distinct `last_success_at` and `last_error_at` alongside last run status/error. Existing UI remains unchanged and continues to show raw registry status/detail; no fake HEALTHY labels introduced.
- App data storage is SQLite. `sources`, `monitoring_runs`, `raw_items`, `project_sources` retain source and run evidence. No DB migrations, source deletions, or history edits were made.
